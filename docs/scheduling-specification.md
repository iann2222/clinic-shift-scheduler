# 診所排班系統

**規格版本：v1（正式排班邏輯）**

## 一、專案目的

本專案旨在建立一套可重複使用的診所排班系統。系統應能根據指定月份、每日各時段需求、人員職務資格、正職類別、正職與兼職性質、請假限制、個人班次需求及公平性原則，自動產生符合條件的排班表。建議使用 Python 搭配 Google OR-Tools CP-SAT 求解器實作。

系統的主要目標如下：確保所有必要班次均有人員負責；確保所有硬性限制均被遵守；依正職 A 類與 B 類的不同規則，安排合理的每日班次組合；A 類正職絕對不得一天安排三節班；B 類正職可安排早上、下午、晚上三節班，但絕對不得出現僅安排早上加晚上的非連續雙班；兼職人員每天最多安排兩節並永久禁止三節班；兼顧相同公平性群組內人員的排班公平性；在同一個 CP-SAT 模型中以最佳化政策優先滿足正職班次需求並由兼職承接其餘需求，不得先固定一張正職班表後再另外填入兼職；支援人員請假與不可排時段；能正確區分輸入錯誤、前置檢查無解、求解器證明無解、可行但未證明最佳及未知等狀態；能輸出排班結果、個人統計與違規檢查結果。

## 二、適用範圍

本系統 v1 適用於診所或其他具有下列特性的排班情境：每日固定包含且僅包含依序排列的早上 `morning`、下午 `afternoon`、晚上 `evening` 三個時段；每個時段可能包含不同工作職務；同一職務在同一時段可能需要一人或多人；人員可能只能執行部分職務；人員可能具有固定總班次、班次範圍或目標班次；正職人員依每日班次規則分為 A 類與 B 類；人員分為正職與兼職；人員可能具有指定可排或不可排時段；排班結果需要考慮連續班次、每日班次組合及公平性。任意時段數量、自訂時段順序與一般化班型不屬於 v1，列為未來版本功能。

v1 只執行本文件明訂的限制，不自行推定或驗證未明訂的勞動法規、跨日最低休息時間、晚班後隔日早班限制、每週休息日、連續工作天數或其他契約條件。v1 也不提供「偏好但非必要」或「希望避免但非禁止」的個人時段偏好；`available_slots` 表示允許，`unavailable_slots` 與請假表示禁止。若未來需要上述限制或偏好，必須先增加明確的輸入欄位、規則、優先級與驗收案例，才能納入模型。使用者仍須自行確認正式班表符合所在地法令與契約。

## 三、基本名詞

**節**：一個人在某一天的一個時段執行一項職務，視為一節。例如 2024/10/01 早上櫃檯為一節，2024/10/01 下午跟診為一節；若同一人在同一天早上及下午各有一個班，則共計兩節。

**時段**：v1 固定為依序排列的早上 `morning`、下午 `afternoon`、晚上 `evening`，不得增加、刪除、改名或改變順序。資料層可保留未來擴充空間，但 v1 不處理其他時段集合或一般化班型。

**職務**：目前主要職務為櫃檯掛號、跟診。未來可擴充為其他職務，例如藥局、行政、清潔或其他工作。

**正職人員**：通常具有指定應排節數或目標節數，其班次應優先安排。正職人員依每日班次組合規則分為 A 類與 B 類，兩者差異在於排班喜好的優先次序不同，以及硬性限制條件不同。

**A 類正職人員**：每日班次組合優先順序為：第一優先一天連續兩節（早上加下午或下午加晚上）；第二優先一天早上加晚上；第三優先一天只安排一節。A 類正職一天最多只能安排兩節，絕對不得安排早上、下午、晚上三節班。

**B 類正職人員**：每日班次組合的正式需求順序為：第一優先盡可能避免單節出勤日；第二優先一天連續兩節（早上加下午或下午加晚上）；前兩項處理後才考慮以早上、下午、晚上完整三節班承接其餘班次。B 類正職每人每個排班月份最多只能有 3 個單節出勤日，理想值仍為 0。B 類正職不得出現「只安排早上與晚上、下午未安排」的非連續雙班。完整三節班因包含下午班，不視為被禁止的早上加晚上組合，也不得誤計為連續雙班。

**兼職人員**：會提供自己可上班的特定日期、時段及可選的職務範圍，該時段只代表允許被安排，不代表必須排滿。兼職人員在同一個 CP-SAT 模型中承接正職班次需求以外的需求。v1 兼職每天最多安排兩節，永久禁止一天三節，不提供例外設定。

**可排時段**：人員可以被安排的日期、時段及職務範圍。正職未提供額外限制時，預設所有開診時段均可排；兼職預設全部不可排，只能使用明確列出的 `available_slots`。可排時段仍須與人員職務資格、實際需求及其他硬性限制取交集。

**不可排時段**：因請假、休假、私人因素或其他限制，人員不得被安排的日期與時段。`leave_requests` 與 `unavailable_slots` 永遠優先於 `available_slots`；同一日期與時段同時出現在允許與禁止集合時，該時段視為不可排。

**連續雙班**：同一人同一天安排早上加下午，或下午加晚上，且該日沒有第三個時段班次。為正確區分 B 類的三節班，系統統計連續雙班時，應將「恰好早上加下午」及「恰好下午加晚上」與三節班分開計算。

**非連續雙班**：同一人同一天只安排早上加晚上，下午沒有排班。此組合對 A 類正職可以安排，但優先度低於連續雙班；對 B 類正職則屬於禁止組合。

**三節班**：同一人同一天早上、下午、晚上均有排班，只允許安排給 B 類正職人員，A 類正職與兼職人員不得安排。

**單節出勤日**：同一人在某一天恰好只有一節班。

## 四、輸入資料需求

系統應至少接受以下資料。

輸入分為「使用者編輯層」與「canonical v1 層」。使用者不需要逐日重複填寫固定需求；可使用版本化的每週需求範本，將星期一至星期日分組，對每組提供 `is_open` 及營業時早上、下午、晚上各職務的完整人數，另以少量日期例外表示臨時休診或不同人力。前處理器必須先依實際日期與星期展開成 canonical v1 的逐日需求，再交給下列完整性驗證、正規化及求解流程。`is_open = false` 的星期或日期不得再提供人力值，展開後視為休診且不建立需求紀錄；`is_open = true` 時仍必須完整提供三個時段及所有職務，包含明確的 0。這一層只是減少重複輸入，不得改變 canonical v1 的硬性規則或自動猜測缺漏值。

**（一）排班期間**：包含排班開始日期、結束日期、每週固定休診日 `closed_weekdays`、額外休診日期 `closed_dates` 及假日標記 `holidays`。休診集合為排班期間內符合 `closed_weekdays` 的日期與 `closed_dates` 的聯集；v1 不提供臨時開診覆寫休診規則。系統必須自行依日期計算星期，不接受人工星期資料作為真實來源。星期日由日期計算；「假日」只作獨立標記，不會自動成為休診日，且必須由輸入明確提供，v1 不自行下載或推定國定假日。休診日不得存在任何班次需求；若休診日仍提供需求，應回報 `INPUT_INVALID`，不得靜默忽略。

**（二）每日班次需求**：在 canonical v1 層，每個開診日期、每個固定時段、每個已定義職務都必須明確提供需求人數；這些紀錄可以由前述每週需求範本確定性展開，不要求使用者手工逐日填寫。需求為 0 必須明確填寫 0；欄位或紀錄缺漏表示輸入不完整，應回報 `INPUT_INVALID`，不得把缺漏自動視為 0。資料結構範例：日期 2024/10/01、時段 `evening`、職務 `assistant`、需求人數 2。模型以人員指派總和等於需求人數表示多人需求，不建立「跟診 1」「跟診 2」等職缺序號；這些序號只在輸出層為了顯示多位姓名時產生。

**（三）人員基本資料**：每位人員必須包含全系統唯一且不可重複的 `employee_id`、顯示用姓名 `name`、人員類型（正職或兼職）、正職類別（A 類或 B 類；兼職必須為空或不適用）、可以執行的職務、`shift_mode`、該模式所需的班次欄位、`fairness_group`、指定可排時段及指定不可排時段。所有請假、可排時段、不可排時段、統計及其他跨資料參照一律使用 `employee_id`；姓名不得作為關聯鍵。

資料範例：`FT001` 範例甲，正職，A 類，可執行職務為櫃檯、跟診，`shift_mode = EXACT`，`required_shifts = 36`，`fairness_group = A_GENERAL`。`FT002` 晴雯，正職，B 類，可執行職務為跟診，`shift_mode = EXACT`，`required_shifts = 40`，`fairness_group = B_ASSISTANT`。`PT001` 兼職 A，兼職，可執行職務為跟診，`shift_mode = RANGE`，`min_shifts = 0`、`max_shifts = 6`，只可使用明確列出的 `available_slots`，`fairness_group = PT_ASSISTANT`。

**（四）可排、不可排與請假資料**：所有紀錄至少包含 `employee_id` 與日期；一般時段紀錄另須包含 `period`。可排時段可額外指定職務集合，未指定職務時代表該人所有合格職務。請假資料另包含 `all_day` 及可選備註；`all_day = true` 時不得提供 `period`，並展開為當日三個時段；`all_day = false` 時必須提供 `period`。資料正規化順序為：先建立人員的預設可排集合，再套用 `available_slots`，最後扣除 `unavailable_slots` 與 `leave_requests`；禁止集合永遠優先。日期超出排班期間、未知人員 ID、未知時段或未知職務均為 `INPUT_INVALID`。

**（五）公平性群組**：每位需要參與公平性最佳化的人員必須提供明確的 `fairness_group`。公平性只在相同人員類型、相同正職類別且 `fairness_group` 完全相同的人員之間比較；A 類、B 類與兼職不得共用同一比較集合。單人成組時仍可輸出統計，但不產生差距目標。系統不得依資格、節數、可排時段或請假情形自行猜測誰與誰「條件相近」。若不希望某人參與公平性比較，可讓其使用只包含自己的獨立群組。

**（六）資料完整性與優先關係**：所有列舉值、日期、職務、人員參照及班次欄位都必須通過正式資料結構驗證。重複且內容相同的紀錄應在正規化時去重；互相矛盾的重複紀錄、無法判定的欄位組合或缺漏必填需求一律回報 `INPUT_INVALID`，不得由系統猜測或補值。

## 五、人員班次規則

**（一）人員班次模式**：所有人員都必須且只能選擇一種 `shift_mode`。正職 v1 合法值為 `EXACT`、`RANGE`；兼職合法值為 `EXACT`、`RANGE`、`TARGET`。三種模式互斥。正職使用 `TARGET` 或任一模式使用不合法的欄位組合均回報 `INPUT_INVALID`。

- `EXACT`：只接受 `required_shifts`，實際總節數必須恰好等於該值；不得提供 `target_shifts`、`min_shifts` 或 `max_shifts`。
- `RANGE`：必須提供 `min_shifts` 與 `max_shifts`，且 `0 ≤ min_shifts ≤ max_shifts`；實際總節數必須落在閉區間內；不得提供 `required_shifts` 或 `target_shifts`。
- `TARGET`：必須提供非負整數 `target_shifts`，可選擇提供硬性 `min_shifts`、`max_shifts`，不得提供 `required_shifts`。只有使用者明確提供的硬性界限才參與欄位一致性檢查：若提供 `min_shifts`，必須滿足 `0 ≤ min_shifts ≤ target_shifts`；若提供 `max_shifts`，必須滿足 `target_shifts ≤ max_shifts`；若兩者皆提供，另須滿足 `min_shifts ≤ max_shifts`。未提供的界限不得以個人理論容量補成輸入驗證條件。即使請假、資格、實際需求、每日模式或可排容量使 `target_shifts` 無法達成，也不得因此回報 `INPUT_INVALID`；模型應在所有硬性限制下求解，並以 `|actual_shifts - target_shifts|` 的對稱絕對偏差作為正式最佳化指標，低於與高於目標每一節的成本相同。

任何模式名稱、必要欄位缺漏、禁止欄位混用、負數或上下限次序錯誤都應回報 `INPUT_INVALID`。兼職若無最低需求且不需要個人軟目標，應明確使用 `RANGE` 並設定 `min_shifts = 0`，不得依賴隱含預設。

**（二）A 類正職人員每日班次規則**：每天最多安排兩節，絕對不得安排三節班；合法雙班包括恰好早上加下午、恰好下午加晚上及恰好早上加晚上。品質順序為：第一順位最大化恰好連續雙班；第二順位在第一順位的類別公平結果鎖定後最大化恰好早上加晚上，使其優先於單節出勤日；單節出勤日為最後順位。A 類內部公平性依相同順位，先比較連續雙班比例，再比較早上加晚上比例，最後比較單節日比例；每項只在相同 `fairness_group` 內比較。

**（三）B 類正職人員每日班次規則**：每天最多可以安排三節；每人每個排班月份的單節出勤日總數不得超過 3，且類別第一順位的理想值仍為 0；絕對不得安排恰好早上加晚上、下午未排班的非連續雙班，完整三節班因包含下午班而不屬於此禁止組合。品質順序為：第一順位最小化單節出勤日；第二順位在第一順位的類別公平結果鎖定後最大化恰好連續雙班；完整三節班是處理前兩順位及硬性班次需求後的合法剩餘班型，不建立「最大化 B 三節班」目標。B 類內部公平性依相同順位，比較單節日、連續雙班及三節班比例；每項只在相同 `fairness_group` 內比較，且只能分配已由類別層鎖定的品質負擔，不得為了縮小個人 gap 增加 B 類單節日總數。

**（四）不同正職類別之間的關係**：A、B 類有不同的品質順位，禁止再以「A+B 連續雙班合計」或「A+B 單節日合計」取代各自需求。兩類同級的正式含義為：每一順位先分別求出 A、B 類在既有前置鎖定下可達的單類理想值，再以各自機會日數正規化實際解距離理想值的 regret；共同最小化兩類最大 regret，鎖定後再最小化 regret 總和。不得先鎖定其中一類的理想值而使另一類天然退讓。第一順位比較 A 類「最大化連續雙班」與 B 類「最小化單節日」；第二順位比較 A 類「最大化早上加晚上」與 B 類「最大化連續雙班」。類別內個人公平性在相同類別、相同 `fairness_group` 中依各自順位處理；不再建立跨 A／B、跨群組的全體個人連續雙班比例目標。

**（五）兼職人員**：只可安排在其明確提供的 `available_slots`，該集合代表允許而非必排；實際節數另受 `shift_mode`、職務資格、請假及不可排時段限制。v1 每天最多兩節並永久禁止三節班，不提供個人例外。兼職與正職在同一個 CP-SAT 模型中共同指派；「正職優先、兼職補缺」以先最小化兼職總節數實現，不表示先產生並固定正職班表。`TARGET` 兼職在正職品質結果鎖定後，同時比較全體目標偏差與相同 `fairness_group` 內各人相對自身目標的偏差公平性；不得先把最低總偏差單獨鎖死。非 `TARGET` 兼職才在後續以實際總節數的整數 gap 比較。

## 六、硬性限制

硬性限制是任何情況下均不得違反的規則。

**（一）班次覆蓋**：對每個開診日的 `(date, period, role)`，所有合格人員的安排人數總和必須恰好等於 `demand[date, period, role]`。例如某日晚上的跟診需求為 2，該日期、晚上、跟診職務必須恰好安排兩位互不重複的合格人員。模型內不建立帶序號的獨立職缺。

**（二）職務資格**：人員只能被安排到其具備資格的職務——只能櫃檯的人員不得安排跟診，只能跟診的人員不得安排櫃檯，同時具備兩種資格者可安排任一職務。

**（三）同時段不可重複**：同一人在相同日期、相同時段只能被安排一次，不得同時擔任櫃檯與跟診；同一時段的櫃檯與跟診必須由不同人員擔任。

**（四）A 類正職每日上限**：同一天最多只能安排兩節，不得安排三節班。

**（五）B 類正職每日上限、每月單節上限與禁止組合**：同一天最多可安排三節，每人每個排班月份最多只能有 3 個單節出勤日，且不得出現「早上有班、下午沒有班、晚上有班」的恰好早上加晚上非連續雙班；三節班則可以安排。

**（六）兼職每日上限**：v1 同一天最多只能安排兩節，並永久禁止三節班；不得以個人欄位覆寫此限制。

**（七）連續時段定義**：優先的連續雙班組合為恰好早上加下午、恰好下午加晚上。對 A 類而言，早上加晚上可以安排，但屬於較低優先組合；對 B 類而言，恰好早上加晚上屬於硬性禁止組合。

**（八）請假限制**：人員在請假日期與時段不得被安排，整日請假表示該日所有時段均不得安排。

**（九）休診限制**：休診日不得建立或安排任何班次。休診日若存在需求資料，屬於輸入錯誤而非需求為 0。

**（十）可排時段限制**：正職預設所有開診時段可排，再扣除其不可排與請假時段；若正職明確提供 `available_slots`，該集合用於進一步限縮預設集合。兼職預設全部不可排，只能安排在明確指定的 `available_slots`。所有人員的 `unavailable_slots` 與 `leave_requests` 永遠優先於 `available_slots`。

**（十一）個人班次限制**：`EXACT` 的實際班次必須等於 `required_shifts`；`RANGE` 不得少於 `min_shifts` 或超過 `max_shifts`；`TARGET` 必須遵守其可選的硬性上下限，目標值本身為軟性目標而非固定班次。

**（十二）正職類別必須明確**：每位正職人員必須指定為 A 類或 B 類，若缺漏，系統應在資料驗證階段回報錯誤，不得自行推定。

**（十三）需求資料完整性**：每個開診日期、三個時段及每個已定義職務都必須明確提供非負整數需求。明確的 0 表示不需要人力；缺漏表示輸入不完整，必須回報錯誤。

## 七、排班優先順序

v1 不使用人工式先後填格，也不先固定正職班表再填兼職。所有合法人員與人力需求在同一個 CP-SAT 模型中共同求解，並採嚴格分階段字典序（lexicographic）最佳化。每一階段只有在求解器證明該階段為 `OPTIMAL` 後，才將該目標最佳值以等式鎖定並進入下一階段；不得使用容許退讓。若某階段只取得 `FEASIBLE` 或 `UNKNOWN`，可輸出目前已通過驗證的合法班表及已完成階段資訊，但不得宣稱完整 v1 最佳化流程已完成。

正式且唯一的目標順序如下：

**第一層：硬性限制與可行性。** 套用所有硬性限制並尋找可行解。輸入錯誤、前置檢查無解、求解器證明無解與無法判定必須使用不同狀態回報；含硬性違規的班表不得輸出為正式結果。

**第二層：最小化兼職總使用量。** 正職的 `EXACT` 與 `RANGE` 已由硬性限制處理；本層最小化所有兼職的實際總節數。這是同一模型中的最佳化政策，不表示先求出或固定正職指派。如果全部人員的硬性節數使兼職總量已由「總需求減去正職總量」唯一決定，該目標為常數，求解控制器應記錄常數值並直接跳過不必要的求解。

**第三層：A／B 主要偏好共同保護。** 在第二層最佳值鎖定後，以不互相加鎖的獨立求解分別證明 A 類連續雙班日總數的最大值，以及 B 類單節出勤日總數的最小值。兩個 conditional benchmark 只定義各類在完全相同目前可行域中的理想值，不直接固定最終班表；每個 benchmark 必須為 `OPTIMAL` 或可證明的常數。A 類 regret 為「A 類連續雙班理想最大值 − 實際 A 類連續雙班日數」；B 類 regret 為「實際 B 類單節日數 − B 類單節理想最小值」。各類 regret 依第八章的類別機會日數換算成整數 basis points，先最小化兩類有效 regret 的最大值，鎖定後再最小化兩者總和。機會日數為 0 的類別不參與 max 或 sum；若兩類均無機會日，兩個子階段均為常數 0。

**第四層：A／B 次要偏好共同保護。** 第三層兩個 regret 最佳值鎖定後，再在此時的 conditional 可行域中，以不互相加鎖的獨立求解分別證明 A 類恰好早上加晚上日數的最大值，以及 B 類連續雙班日總數的最大值。A、B 類 regret 均為各自理想最大值減去實際值，仍依各自類別機會日數換算；先最小化兩類最大 regret，再最小化 regret 總和。第二順位 benchmark 與正式目標不得破壞第三層結果。B 類三節班只是合法 fallback，不建立最大化 B 三節班目標。

**第五層：鎖定類別層級品質結果。** 第三、四層完成後，除了鎖定四個 regret 目標值，還必須把 A、B 類各自在兩個順位的實際總值以等式明確鎖定；並將第二順位正式解當下的 A 類單節日總數與 B 類三節班總數記為剩餘班型類別鎖，再允許個人公平性介入。剩餘班型鎖只保存此時已存在的負擔，不對 A 單節日或 B 三節班新增最大化或最小化目標。此步驟不增加正式 objective vector 項目；它用來保證後續階段只能在六個既有類別班型總量中分配班型。

**第六層：類別內個人班型聯合比例公平性。** 只在相同類別且相同 `fairness_group` 內建立個人比例 gap，但將兩類全部正式班型指標放入同一個公平套件：A 類為連續雙班、早上加晚上、單節日；B 類為單節日、連續雙班、三節班。三個嚴格子目標依序為：最小化全部適用 gap 的最大值、最小化第一順位 gap 總和、最小化全部 gap 總和。此層只能分配第五層已鎖定的類別品質結果。

**第七層：各類別內個人班型整數公平性。** 在聯合比例公平性鎖定後，合併最小化所有 A、B 類群組的整數 max-min gap 總和，不得改變第五層類別品質鎖。

**第八層：兼職 TARGET 偏差與相對公平性。** 只納入 `shift_mode = TARGET` 的兼職。每人計算 `deviation_i = abs(actual_i - target_i)` 與 `relative_i = round_half_up(10000 × deviation_i / max(target_i, 1))`。`target_i = 0` 時，實際 0 節為 0 bp，每一節偏差增加 10,000 bp。全體目標損失為 `overall = round_half_up(10000 × sum(deviation_i) / sum(max(target_i, 1)))`；相同 `fairness_group` 至少兩名 TARGET 兼職時，群組 gap 為 `max(relative_i) - min(relative_i)`。先最小化 `overall` 與所有群組 gap 的最大值，鎖定後再最小化 `overall + sum(group_gap)`。此聯合目標不會先鎖死最低絕對偏差，也不要求不同目標工作量的人取得相同實際節數。沒有 TARGET 兼職時兩個子階段均為常數 0。

**第九層：其他兼職整數公平性。** 只比較 `EXACT`／`RANGE` 兼職，並只在相同 `fairness_group` 內最小化實際總節數的群組 max-min gap 總和。TARGET 兼職不參與此實際節數公平性，以免不同個人目標被錯誤拉成相同班次數。

**第十層：其他共同公平性。** 分別在各 `fairness_group` 內計算早班節數、午班節數、晚班節數、週日班次節數及輸入明確標記之假日班次節數的群組內最大差距，並最小化加權總和 `7 × 週日班次節數 gap + 3 ×（早班 gap + 午班 gap + 晚班 gap + 假日 gap）`。因此週日 gap 相對於每一項其他 gap 的重要性為 `7:3`；這仍是單一聯合目標，不表示週日絕對優先，也不新增逐項鎖定。第十一層仍會在前十層鎖定後，以不同比較範圍進一步處理全體正職的週日節數及週日出勤天數；v1 未定義的其他「不受歡迎時段」與跨月歷史公平性不納入此層。

**第十一層：全體正職週日公平性。** 在前十層所有最佳值均已鎖定後，才將全部 A、B 類正職合併為單一比較集合，不分 `full_time_class` 或 `fairness_group`，分別計算每人「週日實際班次節數」與「週日出勤天數」的全體 max-min gap。先最小化兩項 gap 中的最大值，鎖定後再最小化兩項 gap 的總和。此層只從前面所有正式目標品質完全相同的候選解中挑選週日負擔較平均的班表，不得改變 TARGET、兼職使用量、A／B 類偏好、類別內班型公平性或其他已鎖定目標。週日出勤天數依日期去重；同一正職同一週日即使排兩節或三節，仍只計一個週日出勤天數。

## 八、公平性定義

公平性全部屬於軟性目標，不得凌駕於硬性限制及其前面的正式最佳化目標。v1 的比例公平性以整數 basis points 建模，其他公平性仍使用整數次數；CP-SAT 目標不得使用浮點數。

**（一）比較對象**：第三、四層以 A 類全體與 B 類全體作為兩個同級比較單位；第六、七層只比較相同正職類別且相同 `fairness_group` 的人員；第八、九層依 TARGET 與非 TARGET 分開處理兼職。唯一例外是最後的第十一層週日公平性，該層跨 A／B 類及 `fairness_group` 比較全部正職，但不納入兼職。

**（二）類別 regret 與公平性差距**：對最大化指標，`regret_days = ideal_max - actual`；對最小化指標，`regret_days = actual - ideal_min`。`regret_bp = bp(regret_days, opportunity_days)`。同一順位先最小化 A、B 類有效 `regret_bp` 的最大值，再最小化其總和；這使兩類以各自可達理想值衡量退讓程度，不使用任意加權或讓某類 benchmark 先成為最終硬鎖。群組內指標 `m` 的差距為 `gap[g,m] = max(m_i) - min(m_i)`；有效比較對象少於兩人時為 0。

**（三）A 類公平性指標**：第一順位為連續雙班日／出勤日，第二順位為恰好早上加晚上日／出勤日，剩餘班型為單節日／出勤日；整數公平性使用相同三項日數。三項比例 gap 共同參與第六層，只有連續雙班 gap 另參與第一順位 gap 總和。

**（四）B 類公平性指標**：第一順位為單節日／出勤日的差距，第二順位為連續雙班日／出勤日，剩餘班型為三節班日／出勤日；整數公平性使用相同三項日數。三項比例 gap 共同參與第六層，只有單節日 gap 另參與第一順位 gap 總和。個人公平性不得改變第五層鎖定的 B 類單節日總數。

**（五）兼職公平性指標**：TARGET 兼職先使用相對自身目標的偏差 basis points；同組至少兩人時比較該比例的 max-min gap，並與全體 TARGET 總偏差比例共同進入第八層。EXACT／RANGE 兼職才在第九層比較同組實際總節數的絕對差距。兩種比較不得混用。

**（六）其他共同公平性指標**：早班節數、午班節數、晚班節數、週日班次節數及輸入明確標記的假日班次節數。第十層只在各自 `fairness_group` 內把五項整數 gap 合併考量，正式目標值為 `7 × 週日班次節數 gap + 3 ×（早班 gap + 午班 gap + 晚班 gap + 假日 gap）`；未提供假日時假日 gap 為 0。`7:3` 表示週日 gap 相對每一項其他 gap 的權重，不表示週日是獨立的 lexicographic 子階段。星期日與假日分開計數，同一天若同時是星期日與假日，可以分別計入週日與假日指標。第十一層另以全部正職為比較集合，再處理週日節數與週日出勤天數，不取代第十層的群組內共同公平。

**（七）全體正職週日公平性指標**：每位正職的週日實際班次節數，以及至少有一節班的週日出勤天數。兩項均使用整數 max-min gap，不使用比例；先最小化兩項 gap 的最大值，再最小化兩項 gap 總和。少於兩位正職時兩個目標均為常數 0。週日若同時被標記為假日，仍可同時計入前一層的假日指標與本層週日指標。

**（八）比例換算與 0 分母**：對分子 `n`、正分母 `d`，basis points 定義為 `bp(n,d) = floor((10000*n + floor(d/2)) / d)`。個人班型比例分母為個人出勤日；個人出勤日為 0 時顯示 `N/A` 並排除於群組 gap。類別 regret 分母「機會日數」為該類每位正職在正規化後至少具有一個合法、具資格且對應需求大於 0 之候選指派的日期數總和；同一人同一天無論有幾個時段或職務均只計一日。機會日數為 0 時該類 regret 顯示 `N/A` 並排除於類別 max 與 sum。optimizer、獨立 metrics、validator 與報表必須共用完全相同的機會日及 half-up 定義。

## 九、前置可行性檢查

在啟動求解器前，系統應先進行快速檢查。前置檢查只用於偵測資料錯誤及部分可證明的無解條件；通過全部前置檢查不代表整月模型一定可行，最終仍以 CP-SAT 求解結果為準。

**（一）總需求與總供給**：檢查所有人最大可排節數總和是否大於等於總需求節數，若小於則問題必定無解。計算個人最大可排節數時，應同時考慮個人總班次上限、可排日期與時段、請假、職務資格、A 類每天最多兩節、B 類每天最多三節（但不得恰好早上加晚上）及兼職每天固定最多兩節。

**（二）職務供給**：分別檢查各職務的最大供給是否大於等於需求，並考慮多職務資格人員會在不同職務間競爭，不能把同一人在同一時段重複計算。此檢查只能作為必要條件，不能單獨證明排班一定有解。

**（三）日期與時段可用人數**：對每一個日期與時段，建立可用人員到職務需求單位的二分圖，使用匹配或最大流概念檢查是否存在足夠的互不重複人員覆蓋該時段全部職務。例如某日晚上需要一位櫃檯及兩位跟診，必須能匹配到三位互不重複且資格符合的人員。只分別比較各職務人數不足以處理多職務資格競爭。

**（四）個人每日容量檢查**：檢查 `EXACT` 的指定節數及 `RANGE`／`TARGET` 明確提供的硬性最低節數是否可能在排班期間內完成，並檢查明確提供的硬性上下限本身是否合法。`TARGET` 的目標值不是硬性最低值；若兼職的理論容量或實際可行容量低於 `target_shifts`，不得判為 `INPUT_INVALID` 或僅因未達目標而判為無解，而應交由目標偏差最佳化處理。例如兼職只剩 10 個可排日期、每天最多 2 節，若 `target_shifts = 23` 且未提供超過容量的硬性 `min_shifts`，仍可求解並產生至少 3 節偏差。A 類正職若以 `EXACT` 要求 23 節但容量只有 20 節則必定無解。B 類正職仍須考慮每月最多 3 個單節日、禁止早晚非連續雙班、同時段互斥及職務資格，因此實際最大值可能低於粗略容量。兼職只能使用明確提供的可排時段。

**（五）B 類每日組合檢查**：若某一天該人員只有早上與晚上可排、下午不可排，則該日不得同時安排早上與晚上，最多只能擇一安排一節。若早上、下午、晚上均可排，則可形成早上加下午、下午加晚上、三節班或任一單節班，但不得形成恰好早上加晚上。

**（六）正職與兼職結構檢查**：檢查所有人硬性最低節數總和是否超過總需求，並檢查硬性最大容量是否低於總需求。對全部採 `EXACT` 的正職，若其固定節數總和大於總需求則無解；若其固定節數加上其他人員硬性節數使兼職總量成為常數，第二層最佳化可直接跳過。這些檢查不代表實際採兩階段填班，所有指派仍在同一個模型內完成。

**（七）類別與規則完整性檢查**：應檢查所有正職均已指定 A 類或 B 類、`shift_mode` 與其欄位組合合法、`fairness_group` 未混入不相容類型、A 類沒有可覆寫三節班禁止的欄位、B 類沒有可覆寫每月單節日上限或要求早晚非連續雙班的欄位、兼職沒有每日上限或三節班例外欄位，以及所有硬性節數與個人可排容量相容。

## 十、OR-Tools 模型設計建議

**（一）核心決策變數**：定義布林變數 `x[employee, date, period, role]`，值為 1 表示該人被安排在該日期、時段及職務，0 表示未安排。只為日期範圍內、開診時段、已定義職務及具有資格的人員建立候選變數；已知不可排的組合可不建立或固定為 0。每個 `(date, period, role)` 必須加入 `sum_employee(x) = demand[date, period, role]`。同一職務多人需求不建立職缺序號，因此不會因「跟診 1／跟診 2」互換而產生模型對稱性；序號只在輸出層依穩定排序產生。

**（二）時段出勤變數**：`slot_work[人員, 日期, 時段]`，只要該人於該日期及時段有任一職務班次，值即為 1；由於同一人同時段只能擔任一個職務，可令其等於該人於該時段所有職務變數之和，並限制該和最多為 1。

**（三）每日班次數變數**：`daily_count[人員, 日期]`，等於該人當天三個時段的出勤變數總和。A 類限制 ≤ 2，B 類限制 ≤ 3，兼職固定限制 ≤ 2。

**（四）每日出勤變數**：`work_day[人員, 日期]`，只要當天有任一班次，值即為 1，可用 `daily_count ≥ work_day` 及 `daily_count ≤ 每日上限 × work_day` 連結。

**（五）單節日變數**：`single_day[人員, 日期]`，當天恰好一節時為 1。每位 B 類正職另對排班期間涵蓋的每個曆月加入 `sum_date_in_month(single_day[employee,date]) ≤ 3` 的硬性限制。

**（六）恰好早上加下午變數**：`morning_afternoon_only[人員, 日期]`，當且僅當早上有班、下午有班、晚上沒有班時為 1。

**（七）恰好下午加晚上變數**：`afternoon_evening_only[人員, 日期]`，當且僅當早上沒有班、下午有班、晚上有班時為 1。

**（八）恰好早上加晚上變數**：`morning_evening_only[人員, 日期]`，當且僅當早上有班、下午沒有班、晚上有班時為 1。對 A 類可以為 1，但優先度低於連續雙班；對 B 類應加入硬性限制使其恆為 0。

**（九）三節班變數**：`triple_day[人員, 日期]`，當且僅當早上、下午、晚上均有班時為 1。對 A 類及兼職加入硬性限制使其恆為 0；對 B 類可以為 1。B 類先最小化單節日、再最大化連續雙班，因此三節班只承接在前兩順位及硬性條件鎖定後仍無法以更高順位班型完成的班次；不另建立會凌駕前兩順位的三節班總量目標。

**（十）連續雙班總數**：`consecutive_double_count[人員]` 為所有日期的 `morning_afternoon_only` 與 `afternoon_evening_only` 之和，三節班不得同時被計入，否則會造成 B 類三節班被錯誤重複計分。

**（十一）A 類非連續雙班總數**：`a_nonconsecutive_double_count[人員]` 為所有日期的 `morning_evening_only` 之和。

**（十二）B 類三節班總數**：`b_triple_count[人員]` 為所有日期的 `triple_day` 之和。

**（十三）兼職使用變數**：`part_time_count[人員]` 為該兼職人員的實際班次總數；兼職總使用量為所有兼職人員的 `part_time_count` 之和。公平性差距必須依 `fairness_group` 分別建立，不可用涵蓋所有兼職的一個全域差距。

**（十四）類別偏好實際值與 benchmark**：依 A、B 類分別建立兩個順位的實際總值：A 類第一順位為連續雙班日數、第二順位為早上加晚上日數；B 類第一順位為單節日數、第二順位為連續雙班日數。每一順位均在既有前置鎖定下，以兩次彼此獨立的求解證明 A、B 類各自的 conditional ideal；求某類 benchmark 時不得鎖定另一類 benchmark。benchmark 本身不是最終班表的直接等式限制；但該順位的最大 regret 與 regret 總和均最佳化並鎖定後，必須另以等式鎖定兩類實際總值，且 benchmark proof record 必須記錄此 `locked_actual_value`。過去在不同政策或不同可行域得到的 benchmark 只能用於診斷或報表比較，不得代入目前正式 optimizer、metrics 或 validator。

**（十五）類別 regret 公平性變數**：對每個類別及順位建立整數 `regret_days`，最大化指標使用 `ideal_max - actual`，最小化指標使用 `actual - ideal_min`；再依第八章的類別機會日數及 half-up 公式轉為 `regret_bp`。每個順位建立兩類有效 `regret_bp` 的最大值與總和，依序供該順位的最大 regret、總 regret 子目標使用。機會日數為 0 的類別排除於 max 與 sum，不得當作 0% 參與比較。

**（十六）個人比例、整數及其他公平性差距變數**：正職班型比例與整數 gap 分別供第六、七層使用，不得改變第五層類別品質鎖。TARGET 兼職另建立個人相對偏差 basis points、同組 gap、全體偏差比例、最大損失及損失總和；EXACT／RANGE 兼職才建立實際總節數 gap。第十一層另建立全體正職週日節數與出勤天數 gap。

**（十七）每日組合完整性**：由於每日只有三個時段，可透過布林變數完整表示以下互斥組合：未出勤、只上早班、只上下午班、只上晚班、恰好早上加下午、恰好下午加晚上、恰好早上加晚上、三節班。對每位人員、每個日期，上述八種組合應恰好選擇一種，此種「每日模式變數」建模方式通常比僅以多個布林乘積判定更清楚，也更容易實作不同類別的合法模式。

A 類允許模式：未出勤、三種單節模式、早上加下午、下午加晚上、早上加晚上（禁止三節班）。
B 類允許模式：未出勤、三種單節模式、早上加下午、下午加晚上、三節班（禁止早上加晚上）；每日模式合法之外，全月三種單節模式合計仍須受每人最多 3 次的硬性限制。
兼職允許模式：未出勤、三種單節模式、早上加下午、下午加晚上、早上加晚上（永久禁止三節班）。

## 十一、多階段最佳化策略

v1 的求解控制器必須完全依第七章十一層順序執行，不得另定第二套順序。第三、四層各包含最大 regret 與 regret 總和兩個正式子階段；第六層包含三個正職比例公平子階段；第八層包含 TARGET 最大與總正規化損失兩個子階段；第十一層包含兩個週日公平子階段。因此正式結果包含十六筆 stage records（含硬性可行性階段）與十五個 objective vector 值。第三、四層合計產生四筆 preference benchmark proof records；第五層不新增 objective，而是記錄類別品質鎖。每個非恆定正式目標階段都必須求解至 `OPTIMAL`、記錄並鎖定最佳值，再開始下一階段。

若某目標經資料分析可證明為常數，例如所有正職均為 `EXACT` 且覆蓋等式使兼職總量固定，求解控制器可以跳過該次求解，但必須在結果中記錄該階段為 `SKIPPED_CONSTANT`、常數值及判定依據。`SKIPPED_CONSTANT` 是階段狀態，不取代整體求解狀態。

每階段應記錄目標名稱、方向、最佳值、求解狀態、求解時間及是否鎖定。只有所有必要目標階段均為 `OPTIMAL` 或 `SKIPPED_CONSTANT`，且獨立驗證器通過時，整體結果才可標示為 `OPTIMAL`。若已找到合法班表但某階段未證明最佳，整體狀態為 `FEASIBLE`；若求解器未找到解也未證明無解，則為 `UNKNOWN`。

嚴格分階段最佳化執行期間，操作介面預設每 5 秒更新目前使用者步驟、正式流程 stage、累積時間及可取得的 incumbent、best objective bound、gap、解改善與 bound 更新時間；未取得的欄位不得虛構顯示。正式流程以「目前第幾個／共十六個 stage」呈現，另可對應十一層政策整理出的十個人類可讀步驟，但兩者都不得換算為時間百分比。第三、四層開始前所做的 A／B conditional preference benchmark 是正式 stage 之外的額外求解，必須獨立標示 benchmark rank、類別及其自身進度，不得占用正式十六階段的 index。硬性可行性成功後可標示已取得合法班表，並分別記錄首次合法班表時間與全部正式最佳值證明時間。互動式終端以覆寫同一行呈現求解心跳，非互動式 log 保留逐行紀錄；若 richer solver progress 暫時不可用，才退回只顯示累積時間的 heartbeat。CP-SAT 各階段的搜尋空間與證明難度不相等，v1 不顯示假的百分比或精準 ETA。所有進度與 telemetry 只屬觀測資訊，不得影響模型、求解器參數、cancellation、正式 stage locks 或最佳化結果。

允許前一階段最佳值退讓、使用權重交換目標或產生多組取捨方案的功能，統一列為未來的 optional comparison mode。該模式不屬於 v1 正式排班邏輯，不得影響 v1 預設結果、正式驗收或 `OPTIMAL` 的判定。

完整正式班表通過獨立驗證並完成 JSON、Excel、PDF 落盤後，可選擇執行「同品質候選班表數量診斷」。診斷必須保留全部硬性限制、conditional benchmark、類別實際值與所有正式 objective 最佳值等式鎖，清除最終 objective 後只搜尋滿足相同鎖定品質的解；不同班表只按核心 `x[employee,date,period,role]` assignment 判定，模型內輔助變數取值不同不得重複計數。正式輸出的班表本身不列入候選數。預設最多尋找 100 份候選；診斷時間可採固定秒數，或以本次 CP-SAT 正式最佳化實測時間乘上正數比例，預設比例為 `0.2`（五分之一），兩種模式互斥且固定秒數不得與比例混用。若排除已知 assignment 後證明再無解，可回報精確候選數；若達到數量上限、時間上限或由使用者中止，只能回報「至少已找到 N 份」並說明尚未證明是否還有更多。正式輸出完成時必須先列印正式狀態、各段時間及輸出檔案路徑，後續候選搜尋、驗證及輸出使用獨立的「候選處理」訊息標籤；在互動式終端中，「已找到 N 份同品質候選班表」會覆寫同一行，非互動式 log 則保留逐行紀錄。可由中文 key 的使用者 `config.json` 指定候選搜尋上限、診斷時間、保存份數及 JSON／Excel／PDF 格式；設定檔分為實際生效的「使用者設定」與僅供查閱的「預設設定」，所有不參與執行的說明或分隔欄位一律使用 `__...__` 命名並由載入器忽略。指定保存的 assignment 必須重新通過獨立 validator 後才能寫入 `output/候選班表/`，每次正式班表成功落盤後該候選資料夾都會清空重建。候選媒介輸出在診斷搜尋結束後執行，不占用診斷搜尋時限。此診斷是正式輸出後的 optional operation，不修改班表、不影響 objective vector、validation、正式狀態或 result contract；診斷被中止也不得刪除或降級已完成的正式輸出。

## 十二、請假處理原則

請假屬於硬性限制，處理流程如下：讀取請假資料；將整日請假展開為當日所有時段；對該人員、日期與時段的所有職務變數設定為 0；在前置檢查中重新計算可用人力；重新計算該人員在該日可形成的合法每日班次模式；若請假造成無解，系統應回報具體原因。

例如若 B 類人員某日原本早上、下午、晚上均可排，但下午請假，則該日不可同時安排早上與晚上（會形成 B 類禁止的非連續雙班），最多只能安排早上或晚上其中一節。

無解訊息範例：「2024/10/15 晚上需要 1 位櫃檯及 2 位跟診，符合資格且未請假的可用人員只有 2 位，因此該時段至少缺少 1 人。」

另一無解訊息範例：「B 類人員晴雯在 2024/10/15 下午請假。該日早上與晚上雖均可上班，但 B 類不得安排恰好早上加晚上，因此晴雯當日最多只能承接其中 1 節，造成當日總容量不足 1 節。」

## 十三、兼職處理原則

兼職者預設全部時段不可排，`available_slots` 是唯一的允許集合而非必排集合。不在集合中的變數固定為 0 或不建立；集合中的變數仍可為 0 或 1，並受職務資格、`unavailable_slots`、`leave_requests`、`shift_mode` 及其他硬性限制約束。`unavailable_slots` 與 `leave_requests` 永遠優先。兼職必須明確提供 `EXACT` 或 `RANGE` 班次模式；若沒有最低班次要求，使用 `RANGE` 並填 `min_shifts = 0`。v1 兼職每天最多兩節且永久禁止三節班，不存在覆寫例外。

兼職與正職在同一個 CP-SAT 模型中共同求解。「兼職補缺」正式定義為：在正職 `EXACT`／`RANGE` 硬性界限下，第一個軟性目標先最小化兼職總使用量；不得先固定正職日期或職務指派後再建立第二個兼職模型。若兼職總量由硬性節數與總需求唯一決定，該階段可直接跳過。

TARGET 兼職以相對自身目標的偏差比例在相同 `fairness_group` 內比較；EXACT／RANGE 兼職才以實際總節數的整數最大差距最佳化。可排時段數與使用比例仍可作報表資訊，但不得取代正式公平指標。

## 十四、排班表輸出格式

月班表正式採日期橫向格式：前兩欄為列標題，其後每一欄代表排班期間的一個日期；第一列為日期，第二列為系統計算的星期，左上角「日期」與「星期」各自橫跨前兩欄且不使用底色。第三列起固定分成早、午、晚三組，每組第一欄將三列合併顯示「早」、「午」或「晚」，第二欄依序顯示「櫃台」、「一診」、「二診」，並沿用該時段既有底色。即使某時段沒有第二位跟診需求，仍保留「二診」列並顯示「—」；「一診／二診」只是輸出層的穩定顯示序號，模型內不存在獨立職缺。左側兩個標題欄採緊湊寬度，Excel 分別為約 3、5 個字元寬，PDF 分別約 4.5、7.5 mm。姓名依 `employee_id` 穩定規則排序填入；明確需求為 0 的格子標示為「—」，休診日整欄標示為「休診」。每個有效儲存格只填一位人員姓名。輸出層必須依 `employee_id` 排序，從固定色盤穩定分配可辨識的文字顏色，不得以姓名建立特例；同一員工在 Excel 月班表、個人摘要及由 Excel 產生的 PDF 中均使用相同顏色。正式色盤前六色依序為 `#2860AD`、`#AD2833`、`#28AD60`、`#8128AD`、`#AD8128`、`#28A2AD`，色彩以 HSL 彩度 62%、明度 42% 為共同基準並優先保持至少 30 度的色相間距。顏色只協助辨識，不影響任何排班規則或統計。

正式 Excel 工作表依一般使用者的閱讀順序固定為：「月班表」、「個人班型摘要」、「個人詳細統計」、「類別與公平性統計」、「求解與驗證資訊」。其中「個人班型摘要」只呈現姓名、類別、總班次、出勤日，以及連續雙班、單節日、早上加晚上拆班、三節班各自的日數／出勤日，另以兩個整數欄位分別列出「週日節數」與「週日出勤天數」；班型比例均顯示為 `X / Y（Z%）`，例如 `17 / 19（89.5%）`，出勤日為 0 時顯示 `0 / 0（N/A）`。完整職務、時段、請假、可排容量及其他比例仍保留在「個人詳細統計」，不得因新增摘要頁而刪除。

正式 JSON 使用獨立版本化的 result contract，目前 contract version 為 `1.11`。`objective_vector` 包含十六筆 stage records 中除硬性可行性外的十五個正式目標值；`part_time_target_max_regret`、`part_time_target_total_regret` 與既有偏好 benchmark／class lock 語意維持不變。`1.11` 只增加求解觀測資訊：每個實際求解 stage 可保存 best objective bound、conflicts 與 branches，另保存不含姓名的問題規模、首次取得合法班表時間、證明完整正式最佳值時間與最佳化總時間；不得以這些資料改變 objective、正式狀態或驗證結果。個人統計仍保存 TARGET 的目標值、絕對偏差及相對偏差 basis points；兼職群組統計仍保存 TARGET 相對偏差與群組 gap。

正式 PDF 是由已完成驗證的正式 Excel 直接產生的單頁 A4 橫向列印版，上方為「月班表」，下方直接接續 Excel「個人班型摘要」的完整表格；摘要表不另加區塊標題，但保留欄位表頭。PDF 表格使用較深色且較粗的框線與粗體文字，時段、週末、休診及摘要表頭底色保持可辨識的中等對比，兼顧螢幕閱讀與列印。為維持單頁列印寬度，PDF 摘要可將 Excel 的「週日出勤天數」欄標題縮寫為「週日天數」，並將姓名欄寬縮為約 11 mm；這只是媒介呈現，統計數值與 Excel／JSON 欄位不變。PDF 不包含個人詳細統計、公平性統計或求解資訊。PDF exporter 只能讀取 Excel 已有的班表與摘要內容及呈現資訊，不得重新計算排班規則、最佳化目標或統計；來源 Excel 必須為完整 `OPTIMAL` 且 validation `PASS`，否則不得產生正式 PDF。正式檔名為 `排班結果_YYYY-MM.result-v1.pdf`，與同月份 JSON／Excel 共用名稱主幹，預設禁止覆寫。

輸出時可選擇額外標示人員類別，但正式班表儲存格仍以姓名為主，例如可在姓名旁附註「範例甲（A）」「晴雯（B）」「兼職 A（兼）」；若為避免版面過於擁擠，也可僅在個人班型摘要及個人詳細統計中標示類別。

## 十六、結果驗證器

求解器完成後，應由獨立驗證器重新檢查結果。驗證器不應依賴求解模型內部的衍生變數，而應從最終班表重新計算所有班次及每日模式。驗證項目至少包含：每個 `(日期, 時段, 職務)` 的安排人數是否恰好等於明確需求；是否有多排或重複排班；職務資格是否正確；同一人是否在同一時段出現兩次；同時段不同職務是否由互不重複的人員擔任；A 類正職是否有人一天超過兩節或出現三節班；B 類正職是否有人一天超過三節、每月單節出勤日超過 3，或出現恰好早上加晚上的非連續雙班；B 類三節班是否完整包含三個時段；兼職是否有人一天超過兩節或出現三節班；是否有人被排在請假或不可排時段；兼職是否被排在未提供的可排時段；`EXACT`、`RANGE` 及 `TARGET` 明確提供的硬性 min/max 是否達成；`TARGET` 實際偏差是否正確重算；休診日是否被排班；排班總數是否等於需求總數；每位正職是否已正確指定 A 類或 B 類；每日模式統計是否與實際時段一致；三節班是否被錯誤重複計入連續雙班；四筆 preference benchmark 的類別、順位、指標、方向、機會日、最佳證明與 `locked_actual_value` 是否完整一致；類別實際值、regret 日數及 regret basis points 是否依共同規則重算；最終解是否不可能優於所記錄的理想值；最終類別實際值是否等於所記錄的品質鎖；個人比例與整數公平性是否只在合法的 `fairness_group` 內計算；各階段已鎖定的最佳值是否能由最終班表重新計算得到。

若驗證失敗，班表不得作為正式輸出。驗證報告應至少包含違規類型、人員、日期、時段、職務、實際值、規定值、建議檢查方向。

## 十七、無解處理

系統必須使用以下互斥的整體狀態，不得只顯示「排班失敗」：

- `INPUT_INVALID`：資料格式、必要欄位、跨資料參照、列舉值、需求完整性、休診需求衝突、`shift_mode` 欄位組合或 `fairness_group` 結構不合法；尚未進入求解。
- `PRECHECK_INFEASIBLE`：前置檢查已由必要條件證明不可能有解；尚未由 CP-SAT 證明。
- `INFEASIBLE`：CP-SAT 已正式證明目前全部硬性限制無法同時滿足。只有此狀態可以宣稱「求解器證明無解」。
- `FEASIBLE`：已找到並經獨立驗證器確認合法的班表，但至少一個必要最佳化階段尚未證明最佳或未完成；不得宣稱是最佳班表。
- `OPTIMAL`：所有非恆定正式最佳化階段都已證明最佳、最佳值已依序鎖定，且最終班表通過獨立驗證器。
- `UNKNOWN`：求解器在時間或資源限制內未找到可行解，也未證明無解；不得宣稱有解或無解。
- `VALIDATION_FAILED`：求解器提供候選班表，但獨立驗證器發現硬性違規或鎖定目標值不一致；班表不得作為正式結果。

當狀態為 `PRECHECK_INFEASIBLE` 或 `INFEASIBLE` 時，系統應盡量提供可理解的衝突資訊，例如：總人力不足；特定職務人力不足；特定日期或時段無法完成匹配；請假造成衝突；某人的硬性最低或固定節數過高；硬性最低節數總和超過需求；兼職可排時段與需求不重疊；A 類每日容量不足；B 類禁止早上加晚上造成容量不足；兼職每日兩節上限造成容量不足；或需求結構無法配合硬性班次限制。

無解訊息範例：「A 類人員範例甲固定需要 23 節，但排班期間內只有 10 個可排日期。A 類每天最多 2 節，因此最大容量為 20 節，至少不足 3 節。」

「B 類人員晴雯在 2024/10/08 只有早上及晚上可排，下午不可排。由於 B 類禁止恰好早上加晚上，因此當日最多只能安排 1 節，無法承接原先預估的 2 節。」

「2024/10/15 晚上需要 1 位櫃檯及 2 位跟診，符合資格且未請假的可用人員只有 2 位，因此該時段至少缺少 1 人。」

若需要更進階的無解分析，可對限制加上假設變數，利用 CP-SAT 的不可行核心功能找出一組造成衝突的限制集合。可加上假設標籤的限制包括：個人固定節數、個人最低節數、請假限制、可排時段限制、A 類每日兩節上限、B 類早上加晚上禁止限制、兼職每日與總班次上限、特定職務需求、特定日期與時段需求。不可行核心不保證最小、唯一，也不保證是完整的營運根因；系統應將該集合轉換為管理者可理解的文字並保留此限制說明，不得只顯示內部變數名稱。

## 十九、系統模組建議

建議將程式拆分為以下模組：資料讀取模組（讀取月份、需求、人員、正職類別、`shift_mode`、`fairness_group`、可排／不可排時段及請假資料）；資料標準化模組（統一日期、星期、假日、職務、固定時段、人員 ID、顯示姓名、人員類型及正職類別格式）；前置驗證模組（檢查輸入錯誤及部分可證明無解）；每日模式模組（依 A 類、B 類及兼職分別定義合法模式）；排班模型模組（建立無職缺序號的 CP-SAT 變數、限制與目標）；求解控制模組（依唯一順序執行嚴格分階段最佳化、鎖定最佳值並管理求解時間與狀態）；結果驗證模組（從最終班表獨立檢查所有硬性規則及鎖定目標值）；統計分析模組（依公平性群組計算正職班型 basis points、比例 gap、整數 gap 及其他報表比例）；無解分析模組（整理前置檢查、求解狀態及不可行核心）；輸出模組（由媒介無關正式結果模型產生日期橫向班表、個人班型摘要、個人詳細統計、類別與公平性統計、整體統計及求解／驗證報告）。

## 二十、公開排班範例與領域設計參考原則

本系統開發時，應參考成熟排班工具的建模方法與領域設計，但不應直接照搬其範例規則或資料結構。Google OR-Tools 官方員工排班範例可作為 CP-SAT 基礎模型的參考，包含人員與班次指派變數、每個班次的人力覆蓋、同一人同時段只能接受一項指派、人員班次上下限，以及在合法解之間改善班次分配等常見做法。正式實作時，應將這些通用結構抽離成可重複使用的模型元件，再加入本系統特有的職務資格、正職固定節數、A 類與 B 類每日模式、兼職可排時段、請假及多階段最佳化規則。

領域資料的劃分方式可參考 Timefold Employee Shift Scheduling 所採用的概念，將排班問題明確區分為人員、技能或職務資格、班次或需求、可用與不可用時段、個人偏好、工作量限制、契約條件、輪班模式及最佳化限制等不同領域物件。即使本系統實際使用 OR-Tools，而非直接使用 Timefold，也應維持類似的職責分離，避免將所有欄位與規則集中在單一資料表或單一求解函式中。

系統內部應將限制依重要性分類。硬性限制代表任何正式班表都不得違反；軟性目標則依正式順序改善正職班型、類別偏好 regret、兼職 TARGET 偏差與公平性、其他兼職負擔、時段分布及假日分布。本系統仍採多階段最佳化策略，不直接套用單一綜合分數。

公開範例主要用於參考模型結構、程式組織、限制表示方法及測試方式，不得視為已符合本診所需求的完整解決方案。尤其 A 類先連續雙班再早晚雙班、B 類先避免單節日再安排連續雙班、A／B 類各自理想值與 regret 公平性、B 類三節班必須與恰好連續雙班分開統計、兼職永久禁止三節班、只在明確 `fairness_group` 內比較個人公平性，以及各階段最佳值嚴格鎖定等規則，均屬本系統的特定營運政策，必須獨立建模、測試與驗證。

建議開發時建立一組「公開範例對照測試」，先以簡化資料確認人力覆蓋、資格限制、可用時段及班次上下限等通用模型行為，再逐步加入 A 類、B 類、兼職、請假、公平性與多階段目標。每次參考或改寫外部範例後，均應由本系統的獨立結果驗證器重新檢查，不得僅因求解器回傳可行或最佳狀態，就認定班表符合本專案規格。

## 二十一、開發階段建議

**第一階段：資料模型與資料驗證**——版本化輸入契約、唯一 `employee_id`、固定三時段、完整需求與明確 0、休診／假日、職務資格、`shift_mode` 互斥欄位、`fairness_group`、可排／不可排／請假優先關係及 `INPUT_INVALID` 測試。

**第二階段：覆蓋與每日模式硬性規則**——以 `x[employee,date,period,role]` 建模需求總和、資格與同時段互斥；實作 A 類每天最多兩節及禁止三節班、B 類每天最多三節、每人每月單節日最多 3 次及禁止恰好早上加晚上、兼職每天最多兩節及永久禁止三節班，以及每日模式互斥與完整性。

**第三階段：可用性與前置可行性**——正職預設可排、兼職明確允許集合、請假與不可排優先、整日請假展開、日期時段匹配／最大流檢查、個人容量檢查及 `PRECHECK_INFEASIBLE` 測試。

**第四階段：班次需求與兼職使用量**——實作 `EXACT`、`RANGE` 與 TARGET 明確 min/max 硬性限制、同一模型中的兼職總使用量最小化及常數階段跳過。

**第五階段：A／B 類別偏好最佳化**——依正式順序建立 A 類「連續雙班、早晚雙班、單節日」與 B 類「避免單節日、連續雙班、三節班 fallback」的不同偏好順位；每一順位先獨立證明兩類 conditional ideal，再以機會日正規化 regret 的最大值與總和公平分配必要退讓，最後鎖定兩類實際品質總值，且不得先鎖定任何一類的理想班表或建立最大化 B 三節班目標。

**第六階段：類別內與其他公平性最佳化**——在兩個類別偏好順位的 regret 最佳值全部鎖定後，將 A、B 類各自相同 `fairness_group` 內的三項個人班型比例 gap 放入聯合 minimax 公平套件，依序最小化最差 gap、第一順位 gap 總和及全部 gap 總和；不再逐項鎖定比例。接著以相同指標的整數 max-min gap 作 tie-breaker，再處理兼職及其他共同公平性，最後才跨類別與群組處理全體正職週日節數及週日出勤天數公平。除這個明訂的最後週日 tie-breaker 外，個人公平性不得跨 A／B 類或跨 `fairness_group` 比較。

**第七階段：求解狀態、無解分析與統計輸出**——完整狀態映射、正式 stage records、四筆 preference benchmark proof records、不可行核心限制說明、A／B 類別偏好 actual／ideal／regret／opportunity、個人班型 basis points／比例 gap、整數公平性指標及其他報表比例。

**第八階段：輸出與獨立驗證**——日期橫向月班表、個人與群組統計、硬性 Pass/Fail 報告、鎖定目標值重算及最佳化品質驗收。多方案與容許退讓不屬於 v1。

## 二十二、驗收標準

驗收分為「硬性驗證」與「最佳化品質驗收」，兩者不得混用。硬性規則逐項輸出 `PASS` 或 `FAIL`；最佳化品質以各階段目標值及求解證明狀態判定，不要求固定姓名出現在固定格子，因為同一目標向量可能有多張等價班表。

### 硬性驗證

至少包含以下逐項 Pass/Fail 測試：輸入資料符合版本化契約；每個開診日期、時段與職務需求均明確提供；休診日沒有需求或排班；每個需求的人員總和恰好等於需求數；所有人具備對應職務資格；同一人同時段最多一項職務；請假與不可排時段無排班；正職預設可用及兼職明確可用集合的語意正確；`EXACT`、`RANGE` 及 `TARGET` 明確提供的硬性 min/max 成立；A 類每天最多兩節且無三節班；B 類每天最多三節、每人每月單節日最多 3 次、無恰好早上加晚上，三節班完整包含三個時段；兼職每天最多兩節且無三節班；每日八種模式恰選一種；總排班節數等於總需求節數；三節班未計入連續雙班；公平性群組未跨不相容類型；日期橫向輸出每個展開後的有效儲存格只有一個姓名；四個順位類別實際鎖及 A 單節／B 三節兩個剩餘班型鎖均與最終重算一致；獨立驗證器重算結果與輸出統計一致。任一項 `FAIL` 時整體狀態必須為 `VALIDATION_FAILED`，班表不得標示為正式結果。

輸入錯誤案例必須驗證會回傳 `INPUT_INVALID`；另須包含「TARGET 高於可排容量但未提供矛盾硬性 min/max」的案例，確認系統仍進入求解並輸出正確絕對偏差，而不是回傳 `INPUT_INVALID`。前置必要條件可證明無解的案例必須回傳 `PRECHECK_INFEASIBLE`；由求解器證明無解的案例必須回傳 `INFEASIBLE`；逾時且未判定的案例必須正確區分 `FEASIBLE` 與 `UNKNOWN`。

### 最佳化品質驗收

應建立可人工推導或以窮舉確認最佳值的小型固定測試資料，依序驗證兼職總使用量、兩個正職偏好順位的 max／total regret、正職個人比例與整數 gap、兼職 TARGET 最大／總正規化損失、其他兼職總節數 gap、共同公平性及全體正職週日公平。TARGET 測試必須涵蓋不同目標工作量、相對偏差公平、群組隔離、target 為 0、half-up rounding，以及 optimizer／result metrics／validator 重算一致。每個正式階段都必須證明 `OPTIMAL` 並鎖定精確最佳值，後一階段不得改變前一階段值。

品質測試比較的是正式目標值、方向、順序與鎖定結果，而不是完整姓名班表。若測試只取得合法解但未證明某階段最佳，最多只能驗收為 `FEASIBLE`，不能通過完整 `OPTIMAL` 品質驗收。另應使用隨機或組合式小型案例，由獨立驗證器重算硬性條件與目標向量，防止模型與報表同時使用相同錯誤邏輯。

## 二十三、結論

本文件定義單一且一致的 v1 規格。v1 固定使用 `morning`、`afternoon`、`evening` 三個有序時段；核心變數為 `x[employee,date,period,role]`，多人需求以人員總和等於需求數表示，職缺序號只在日期橫向輸出層產生。請假與不可排時段是硬性禁止；正職預設所有開診時段可排，兼職預設全部不可排並只能使用明確允許集合。

A 類每天最多兩節且禁止三節班；B 類每天最多三節、每人每月單節出勤日最多 3 次、禁止恰好早上加晚上但允許完整三節班；兼職每天最多兩節且永久禁止三節班。B 類三節班不得重複計入連續雙班，也不建立最大化 B 三節班目標。所有人以唯一 `employee_id` 關聯資料，姓名只供顯示；班次模式欄位嚴格依 `EXACT`、`RANGE`、`TARGET` 互斥規則驗證。

正式排班在同一個 CP-SAT 模型中採嚴格分階段 lexicographic optimization：硬性限制與可行性、兼職總使用量、正職主要與次要偏好 conditional benchmark／regret、類別品質鎖、正職個人比例與整數公平、兼職 TARGET 偏差／相對公平、其他兼職整數公平、共同公平性，最後才處理全體正職週日公平。A 類的順位是連續雙班、早晚雙班、單節日；B 類的順位是避免單節日、連續雙班、三節班 fallback。TARGET 兼職以自身目標作為比例基準，不要求不同目標工作量的人取得相同實際節數；其總偏差與群組相對偏差 gap 在同一公平套件中共同處理。一般個人配對只存在於相容類型且相同 `fairness_group` 內；唯一跨類及跨群組比較是最後的全體正職週日公平 tie-breaker。

容許退讓、多方案取捨、任意時段數量、一般化班型、未明訂勞動法規與跨日限制均不屬於 v1；前兩者可在未來 optional comparison mode 中另行定義。求解結果必須使用正式狀態集合並通過獨立驗證器；只有全部必要階段均證明最佳且驗證通過時才能標示 `OPTIMAL`。

因此，v1 可使用 Python、Google OR-Tools CP-SAT、每日模式建模、嚴格分階段求解、前置檢查、獨立結果驗證及日期橫向表格輸出完成，不需要多 Agent 架構。
